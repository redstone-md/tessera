# Native presentation uses Slint

The first presentation module uses [Slint](https://slint.dev/) 1.18.1 with its native winit backend and operating-system accessibility integration. Windows composition enables Slint's native FemtoVG/OpenGL renderer with the software renderer retained as the toolkit's automatic startup fallback; portable pixel tests use software rendering. The `.slint` descriptions compile into Rust; they are not HTML, CSS, or a WebView interface. The host uses first-party standard widgets instead of rebuilding focus, button, or accessibility mechanics.

Slint and Iced were evaluated as maintained native Rust toolkits. Slint was selected for its declarative custom-component model, explicit accessibility support, and stable 1.x interface, which fit a customizable shell. This costs a larger dependency graph and raises the workspace minimum Rust version to 1.92, required by the current Slint release. Keeping an older toolkit solely to preserve the earlier 1.85 minimum was rejected.

Default toolkit features are disabled. The workspace enables `std`, `backend-winit`, `renderer-software`, `accessibility`, and `compat-1-18`; Windows composition adds `renderer-femtovg` and the documented `raw-window-handle-06` bridge for validated owned surfaces. Windows presentation also uses the pinned toolkit's `unstable-winit-030` creation hook; development tests enable the same feature for pure window-attribute assertions. Qt, browser rendering, Skia, WGPU, tray support, live inspection servers, and system-testing servers are not enabled. FemtoVG uses the toolkit's existing transparent GL surface support rather than handwritten layered-window presentation. Slint falls back to software when the initial GL driver probe or window creation fails; this is not a runtime GPU-crash recovery mechanism. Both paths remain event-driven with no fixed-frame-rate idle loop.

## Presentation seam

`tessera-ui` receives portable snapshots, application identities/pixels, and monitor context from a `DesktopHost` adapter, not executable command strings. One controller serves the icon dock, toolbar, application menu, and existing framed recovery/settings panel, sharing the observation worker, cached snapshot, scoped event subscription, search, and stale-action guards. Startup, manual Refresh, and coalesced desktop notifications use one asynchronous path. Search projects retained data without observing again or rewriting opaque keys. Explicit activation/launch stays on the input path; Windows owns validation and foreground denial. Preference preview is independent of Save. Weak component handles deliver worker results without retaining a closed surface.

Notifications received before UI routes are installed remain dirty and coalesce into one follow-up observation. Subscription/startup warnings have a separate visible application-menu notice; a successful manual Refresh cannot silently erase the warning that passive updates are unavailable.

The generated Slint module is isolated from handwritten Rust. Win32 integration remains in the platform module; any compiler-generated toolkit unsafe code is not permission to add handwritten FFI to presentation. Selecting Slint does not choose or freeze a plugin runtime, third-party UI protocol, or shell-activation mechanism.

The default desktop presentation follows the standard Seelen UI theme rather than inventing another text-command taskbar. Native leases are UI-thread-affine: the controller retains each host-returned lease in an `Rc<RefCell<_>>` registry and an explicit run-scope guard releases them before component/HWND destruction. Worker completion sends only a weak-component signal, never a native lease. The platform validates live, current-process HWNDs before styling or registering an appbar; diagnostics bypass these mutations. The primary toolbar reserves 32 logical pixels when an Explorer appbar host is available; the dock is content-sized and floating. Scoped WinEvent notifications replace idle desktop polling. A retained UI-thread heartbeat supervises the GUI; a separate minute timer reads only the clock. Fullscreen hiding keeps the event loop alive. Missing icons use an independent generic glyph with the real accessible application label, never guessed executable paths.

Before constructing any desktop component, Windows sets nonactivating native creation attributes through the toolkit hook. This prevents the first bar show from stealing foreground before its native lease attaches. Only user-opened launcher/settings windows request foreground through the owned-HWND platform adapter; Windows denial is nonfatal and reported. No synthetic input or focus-policy bypass is used. Slint retains Windows HWNDs across hide/show, so the bar's intrinsic `NOACTIVATE` role remains until HWND destruction even when its appbar lease is released during fullscreen hiding; other captured styles and work-area reservations are released normally.

## Seelen reference and lifecycle

The visual reference is [Seelen UI v2.8.8](https://github.com/eythaann/Seelen-UI/tree/53274fa9f45ad1b0ebd798e2d464858a213d9022), inspected at commit `53274fa9f45ad1b0ebd798e2d464858a213d9022`, together with its [official screenshots](https://seelen.io/apps/seelen-ui/customizable-shell). The source standard theme, not a customized purple showcase, fixes the baseline:

- Bottom dock: minimum-content centered placement; 40-pixel items, 28-pixel icons, eight-pixel gaps/padding/outer margin, 16-pixel outer radius and ten-pixel item radius.
- Top toolbar: 32 pixels, 16-pixel horizontal insets, 12.8-pixel text; actual user and focused application at the left, native minute clock centered, input language and settings at the right. Unavailable media, workspaces, tray, and telemetry widgets are absent rather than fabricated.
- Application menu: centered, width 55% of the monitor capped at 1,200 logical pixels, height independently 55% of the monitor; ten-pixel outer margin, seven columns, 16-pixel content padding, square tiles with 12.8-pixel labels and a 35.2-pixel label row; real icons, search, pins, and recovery/settings controls.
- Neutral light/dark surfaces, Windows accent, running dots and a half-item-width focused indicator. Translucency is not a promise of native backdrop blur.

Windows translucency still needs interactive driver validation. The software presenter's upstream [alpha support issue](https://github.com/rust-windowing/softbuffer/issues/17) makes clear that incidental Windows alpha is not its supported surface contract. The native GL renderer requests alpha and prefers transparency-capable configurations, but can fall back when a driver cannot provide one. Opaque fallback is preferable to depending on undocumented blur/composition APIs; neither native backdrop blur nor pixel-perfect driver-independent rendering is promised.

These measurements and documented Windows protocols are independently implemented. Seelen's AGPL code, assets, injected taskbar/tray hooks, web renderer, elevated service, and polling restart loop are not included.

Ordinary launch starts a temporary desktop session, not a persistent shell takeover. An independent native supervisor waits for the GUI's first ready heartbeat before hiding the validated primary Explorer taskbar, retains original visibility and all appbar state flags, and restores them on owned-child exit, timeout, or setup failure. Native taskbar show/create events drive re-hiding; there is no idle taskbar polling. Direct visibility calls target only the primary taskbar; [the documented `ABM_SETSTATE` protocol](https://learn.microsoft.com/en-us/windows/win32/shell/abm-setstate) changes Windows taskbar auto-hide state, so secondary-monitor effects require interactive validation rather than an isolation guarantee. Taskbar restoration and appbar removal precede completion. Persistent shell mode retains its additional exact per-user registry recovery. Runtime diagnostics exercise the GUI heartbeat but never mutate taskbar, work area, or sign-in state.

## Verification and limits

The official [preliminary headless testing backend](https://docs.slint.dev/latest/docs/rust/i_slint_backend_testing/) is a development-only dependency. Its version must exactly match Slint and the compiler, so all three are pinned to 1.18.1 and upgraded together. It tests callbacks and UI state without a display; it does not render pixels or validate Windows accessibility, focus, DPI, or antivirus behavior. The production binary must not include its testing or inspection facilities.

Development builds emit static widget metadata for headless element queries; release builds omit it. This is compiler metadata, not a running inspection server. Controller and text-safety tests do not need that metadata; the headless accessible-button assertion runs in debug builds. Real Windows accessibility remains an interactive release check.

The separate renderer tests instantiate the actual generated components on `MinimalSoftwareWindow`, dispatch pointer/keyboard/real 1x–2x scale-factor events, and render pixels. They check callback/accessibility metadata and that an unchanged surface requests no additional draw. `TESSERA_TEST_SCREENSHOTS` optionally exports PPM frames outside the repository. These tests are not screenshots of Windows' GL compositor and do not establish native screen-reader behavior or idle CPU/GPU measurements.

The taskbar lease protects against an owned GUI crash or heartbeat loss while its supervisor is alive. A hard termination of the supervisor cannot run Rust cleanup; the existing independent restore script recovers Winlogon, not an in-memory taskbar lease. Abrupt supervisor termination and independent taskbar recovery therefore remain explicit Windows release-gate scenarios, not a claimed crash-proof guarantee.

Functional parity remains intentionally incomplete: dock application grouping/instance counters, Seelen's default overlap-triggered auto-hide/pointer reveal, global Windows-key menu toggling, tray/media modules, folders, and plugins are not implemented. Owned appbar position-change notifications are registered but are not yet consumed; competing appbars and dynamic DPI/display changes therefore need explicit Windows checks. Do not call this a complete or already pixel-certified 1:1 Seelen replacement.

Alpha.9 introduces this native visual/session redesign; the immutable alpha.8 remains the earlier alongside-Explorer dock. Optional experimental per-user shell activation and independent recovery remain specified in [the recovery decision](0006-per-user-shell-recovery.md). Neither version is a complete Seelen feature replacement: notification area, widgets, plugins, and automatic window layout remain absent. Hosted checks and software-renderer tests do not prove interactive Windows taskbar/appbar behavior, native backdrop appearance, accessibility, or idle resource use. The public unsigned test package is not evidence of Windows 11 or antivirus approval. Interactive testing and the [distribution trust gates](../distribution-and-trust.md) remain prerequisites for a consumer release.
