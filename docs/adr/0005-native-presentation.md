# Native presentation uses Slint

The first presentation module uses [Slint](https://slint.dev/) 1.18.1 with its native winit backend and operating-system accessibility integration. Windows composition enables Slint's native FemtoVG/OpenGL renderer with the software renderer retained as the toolkit's automatic startup fallback; portable pixel tests use software rendering. The `.slint` descriptions compile into Rust; they are not HTML, CSS, or a WebView interface. The host uses first-party standard widgets instead of rebuilding focus, button, or accessibility mechanics.

Slint and Iced were evaluated as maintained native Rust toolkits. Slint was selected for its declarative custom-component model, explicit accessibility support, and stable 1.x interface, which fit a customizable shell. This costs a larger dependency graph and raises the workspace minimum Rust version to 1.92, required by the current Slint release. Keeping an older toolkit solely to preserve the earlier 1.85 minimum was rejected.

Default toolkit features are disabled. The workspace enables `std`, `backend-winit`, `renderer-software`, `accessibility`, and `compat-1-18`; Windows composition adds `renderer-femtovg` and the documented `raw-window-handle-06` bridge for validated owned surfaces. Windows presentation also uses the pinned toolkit's `unstable-winit-030` creation hook; development tests enable the same feature for pure window-attribute assertions. Qt, browser rendering, Skia, WGPU, tray support, live inspection servers, and system-testing servers are not enabled. FemtoVG uses the toolkit's existing transparent GL surface support rather than handwritten layered-window presentation. Slint falls back to software when the initial GL driver probe or window creation fails; this is not a runtime GPU-crash recovery mechanism. Both paths remain event-driven with no fixed-frame-rate idle loop.

## Presentation seam

`tessera-ui` receives portable snapshots, application identities/pixels, and monitor context from a `DesktopHost` adapter, not executable command strings. One controller serves the icon dock, toolbar, application menu, and existing framed recovery/settings panel, sharing the observation worker, cached snapshot, scoped event subscription, search, and stale-action guards. Startup, manual Refresh, and coalesced desktop notifications use one asynchronous path. Search projects retained data without observing again or rewriting opaque keys. Explicit activation/launch stays on the input path; Windows owns validation and foreground denial. Preference preview is independent of Save. Weak component handles deliver worker results without retaining a closed surface.

Notifications received before UI routes are installed remain dirty and coalesce into one follow-up observation. Subscription/startup warnings have a separate visible application-menu notice; a successful manual Refresh cannot silently erase the warning that passive updates are unavailable.

The generated Slint module is isolated from handwritten Rust. Win32 integration remains in the platform module; any compiler-generated toolkit unsafe code is not permission to add handwritten FFI to presentation. Selecting Slint does not choose or freeze a plugin runtime, third-party UI protocol, or shell-activation mechanism.

The default desktop presentation follows the standard Seelen UI theme rather than inventing another text-command taskbar. Native leases are UI-thread-affine: the controller retains each host-returned lease in an `Rc<RefCell<_>>` registry and an explicit run-scope guard releases them before component/HWND destruction. Worker completion sends only a weak-component signal, never a native lease. The platform validates live, current-process HWNDs before styling or registering an appbar; diagnostics bypass these mutations. The primary toolbar reserves 32 logical pixels when an Explorer appbar host is available; the dock is content-sized and floating. Scoped WinEvent notifications replace idle desktop polling. A retained UI-thread heartbeat supervises the GUI; a separate minute timer reads only the clock. Fullscreen hiding keeps the event loop alive. Missing icons use an independent generic glyph with the real accessible application label, never guessed executable paths.

Before constructing any desktop component, Windows sets nonactivating native creation attributes through the toolkit hook. This prevents the first bar show from stealing foreground before its native lease attaches. Only user-opened launcher/settings windows request foreground through the owned-HWND platform adapter; Windows denial is nonfatal and reported. No synthetic input or focus-policy bypass is used. Slint retains Windows HWNDs across hide/show, so the bar's intrinsic `NOACTIVATE` role remains until HWND destruction even when its appbar lease is released during fullscreen hiding; other captured styles and work-area reservations are released normally.

## Seelen reference and lifecycle

The visual reference is [Seelen UI v2.8.8](https://github.com/eythaann/Seelen-UI/tree/53274fa9f45ad1b0ebd798e2d464858a213d9022), inspected at commit `53274fa9f45ad1b0ebd798e2d464858a213d9022`, together with its [official screenshots](https://seelen.io/apps/seelen-ui/customizable-shell). The source standard theme, not a customized purple showcase, fixes the baseline:

- Bottom dock: minimum-content centered placement; 40-pixel items, 28-pixel icons, eight-pixel gaps/padding/outer margin, 16-pixel outer radius and ten-pixel item radius.
- Top toolbar: 32 pixels, 16-pixel horizontal insets, 12.8-pixel text; actual user and focused application at the left, native minute clock centered, input language and settings at the right. Unavailable media, workspaces, tray, and telemetry widgets are absent rather than fabricated.
- Application menu: centered, width 55% of the monitor capped at 1,200 logical pixels, height independently 55% of the monitor; ten-pixel outer margin, seven columns, 16-pixel content padding, square tiles with 12.8-pixel labels and a 35.2-pixel label row; real icons, search, pins, and recovery/settings controls.
- Neutral light/dark surfaces, Windows accent, running dots and a half-item-width focused indicator. Translucency is not a promise of native backdrop blur.

Windows translucency still needs interactive driver validation. The software presenter's upstream [alpha support issue](https://github.com/rust-windowing/softbuffer/issues/17) makes clear that incidental Windows alpha is not its supported surface contract. The native GL renderer requests alpha and prefers transparency-capable configurations, but can fall back when a driver cannot provide one. Opaque fallback is preferable to depending on undocumented blur/composition APIs; neither native backdrop blur nor pixel-perfect driver-independent rendering is promised.

These measurements and documented Windows protocols are independently implemented. Seelen's AGPL code, assets, injected taskbar/tray hooks, web renderer, elevated service, and polling restart loop are not included.

Ordinary launch starts a temporary desktop session, not a persistent shell takeover. An independent native supervisor waits for the GUI's first ready heartbeat before hiding the validated primary Explorer taskbar, retains original visibility and all appbar state flags, and restores them on owned-child exit, timeout, or setup failure. Native taskbar show/create events drive re-hiding; there is no idle taskbar polling. Direct visibility calls target only the primary taskbar; [the documented `ABM_SETSTATE` protocol](https://learn.microsoft.com/en-us/windows/win32/shell/abm-setstate) changes Windows taskbar auto-hide state, so secondary-monitor effects require interactive validation rather than an isolation guarantee. Taskbar restoration and appbar removal precede completion. Persistent shell mode retains its additional exact per-user registry recovery. Runtime diagnostics exercise the GUI heartbeat but never mutate taskbar, work area, or sign-in state.

The settings contract includes monitor/workspace inheritance, theme-variable overrides, wallpaper-instance settings and widget-instance overrides. Application rules distinguish executable and application-model identities, support the reference matching operators and nested negation/and/or groups, and keep bundled defaults readonly. Developer controls preserve their gate and nested tools/colors/components/icons/widget-debug structure.

Each capability is checked in normal, empty, unavailable/denied, loading, error and stale states where applicable. Verification covers genuine input/event paths, persistence/restart, keyboard/accessibility, software pixels, actual Windows geometry/focus/composition, recovery, and idle resources. A missing backend must report unavailable honestly; it is not a completed parity row. Independent implementations and properly licensed icon libraries remain required.

Implementation grows in working layers: bounded diagnostics first; then complete native actions and reusable surface/token/popup boundaries; then actual system providers and their popups; then configuration, resources, workspaces, wallpaper and optional tiling. A new capability is not complete merely because its menu entry or setting exists. System-module events must not turn unrelated desktop-window observation into continuous polling.

## Native interaction layer (alpha.10)

Dock context menus use one lazily created, separately owned Slint `Window`, shared palette/tile primitives and typed actions. On the pinned winit backend, built-in popups are rendered inside their parent and clip to narrow bars; platform `TrackPopupMenu` also blocks the UI timer loop. Neither path is used. The transient `Popup` role is an activatable tool window, unlike the nonactivating bars; user-triggered foreground requests respect Windows denial, and no synthetic input or force-focus API is used. Only the open popup's own focus is sampled for dismissal, not foreign windows or desktop observation.

Window menus activate without toggling, request asynchronous minimize, and post ordinary close requests; they do not terminate applications or claim that a queued request completed. Pin/recovery commands reuse existing persistence and host boundaries. Native identity and application eligibility are revalidated at each platform effect. Popup leases drop before hide, parent callbacks and component teardown. Synchronous Slint appearance callbacks during `show()` coalesce geometry requests so leases are not borrowed recursively and the final UI geometry is applied before readiness.

`inspect --check-surfaces` is a read-only, nonvacuous geometry diagnostic. Its physical toolbar contract is full monitor origin/width and the DPI-scaled 32px token, not the already-reserved work area. It preserves unavailable metadata as unknown and rejects missing/ambiguous/incomplete observations. The Windows fixture drives the same CLI from conformant geometry to a deliberate offset and back, using only its own window and a restored thread DPI context. Portable tests and MSVC cross-target checks do not prove native fixture execution, actual AppBar negotiation, Slint scale, foreground behavior or Windows composition. The reported VM toolbar offset remains unresolved until captured evidence identifies its cause.

The immutable [alpha.10 CI run](https://github.com/redstone-md/tessera/actions/runs/37675695227) passed on Windows stable and Rust 1.92.0, including actual execution of the controlled toolbar green/offset-red/restored-green CLI fixture, and published only after native packaging/runtime preflight passed. This verifies the diagnostic feedback loop, not the cause or correction of the user's VM toolbar offset.

## Next native appearance layer (development)

Post-alpha.10 source uses the independently licensed Lucide Settings2 vector instead of a handmade toolbar gear, alongside the existing Bootstrap Windows vector. Full ISC/MIT notices are bundled and included by the existing package notice scan; no old release asset is replaced.

Interactive popups and passive tooltips share a small native transient-window lifetime boundary. It releases the native lease before hide/replacement/component teardown and rejects foreground requests for passive roles. A synchronous close during show/attachment cancels the transaction instead of publishing a late lease or resurrecting visibility; native hide is deferred until that in-flight lease is discarded. Required main-window attachments are keyed by their semantic surface role, not fixed array indices.

A standalone tooltip primitive now wraps real accessible text, measures against its intended content width before the first native size is assigned, and renders outside the dock bounds at 1x and 2x without idle redraw. Its passive role retains NOACTIVATE; the production host uses Winit's documented cursor hit-test API and native style readback requires both layered and transparent pass-through flags. See [the documented Windows layered-window input rule](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#layered-windows).

Context menus and tooltips now use one independently implemented `PopoverBody` and shared overridable tokens. Defaults follow the [pinned reference design system](https://github.com/eythaann/Seelen-UI/blob/53274fa9f45ad1b0ebd798e2d464858a213d9022/documentation/design-system.md) and [shared popover stylesheet](https://github.com/eythaann/Seelen-UI/blob/53274fa9f45ad1b0ebd798e2d464858a213d9022/src/static/themes/default/shared/index.scss): opaque theme-adaptive base surface, 10px shadow margin and radius, 12.8px type, and the documented medium shadow (2px/2px offset, 8px blur, 16% black). The [tooltip stylesheet](https://github.com/eythaann/Seelen-UI/blob/53274fa9f45ad1b0ebd798e2d464858a213d9022/src/static/themes/default/styles/tooltip.scss) supplies the 500px body cap and 4px/8px padding; no undocumented arrow is invented and no AGPL implementation or assets are copied.

A generic component theme boundary preserves both toolkit and reference color schemes instead of repeating global access at each caller. Delayed tooltips read the owner's current schemes at presentation, alongside its current scale and origin. The shared frame explicitly publishes usable content bounds, excluding its shadow; transcluded children must not derive them from the outer component's `parent` bounds. Actual light/dark 1x/2x rendering checks opaque body pixels and empty bottom padding: visual inspection exposed a clipped final line, and the new assertion reproduced it before the layout correction. Exact reference tooltip markup overrides, native font/line-height, show/hide motion and Windows composition are not yet pixel-certified.

Popover typography now inherits the toolkit's system/default family instead of hardcoding Segoe UI. The [reference reset's `1.4` line-height](https://github.com/eythaann/Seelen-UI/blob/53274fa9f45ad1b0ebd798e2d464858a213d9022/libs/core/styles/reset.css) is font-size-relative; [Slint's `line-height-factor`](https://docs.slint.dev/latest/docs/slint/reference/elements/text/#line-height-factor) is relative to natural font height including line gap. One nonrendering, inaccessible single-line measurement in the shared frame converts between those units using the renderer itself, without guessing font metrics or adding a library. The renderer test verifies 1, 2 and 9 explicit lines at both scales against the expected intrinsic logical-pixel rounding, then renders the wrapped caption and checks its padding. This verifies the unit conversion, not Windows glyph/baseline or system text-scaling parity.

The windowed applications menu now reuses this same opaque frame with its own 16px radius, instead of duplicating its margin/background and omitting the medium shadow required by the [pinned apps-menu stylesheet](https://github.com/eythaann/Seelen-UI/blob/53274fa9f45ad1b0ebd798e2d464858a213d9022/src/static/themes/default/styles/apps-menu.scss). Its focus scope uses the published content width/height, avoiding double margins or shadow-area layout. Light/dark 1x/2x RGBA software checks cover opaque body, transparent exterior, full button rectangles inside the content bounds and no settled idle redraw. Header/footer control styling and full applications-menu behavior remain incomplete.

The applications grid separates clipped icon/name content from the tile's external focus outline. Shared `FocusTokens` publish the stroke, offset and required viewport gutter. Moving that space from surrounding layout padding into the scroll viewport retains the original 16px grid inset, square tile size and 8px gaps while keeping both edge-column outlines visible. A real generated-component test reproduced the clipped outline before correction and verifies first/last-column pixels, unchanged bounds and pointer/Space actions at both themes and scales, with nonempty 32px icon data and a content-overflow guard. This does not certify native Windows focus composition, every scroll position or the dock's clipped overflow edges.

Native transient presentation opts into the shared reference's 150ms ease-out show opacity only after attachment succeeds. Each presentation reads the current host motion permission; the production adapter uses [Windows' read-only `SPI_GETCLIENTAREAANIMATION`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-systemparametersinfow). Unsupported hosts and query failures skip the effect. Cancellation/hide/teardown reset motion immediately and preserve lease-before-HWND cleanup; there is no extra native timer or blocking animation API. A renderer-owned deterministic clock verifies start, midpoint, settled pixels, mid-show cancellation, skipped motion and no settled idle redraw. Slint caches the current tick's animation-activity flag, so cancellation pixels are checked immediately and the flag on the next loop tick. Software rendering applies opacity per child rather than a compositor layer; intermediate Windows GL pixels still require native verification.

Live reduced-motion opt-out settles an already visible tooltip/context menu without hiding it, requesting focus or replacing its native lease. Changing an animation's duration/permission alone did not finish Slint's running tween; a shared imperative opacity setter now explicitly settles it, with a renderer assertion that reproduced the failure first. Production subscribes to [Windows' `UISettings.AnimationsEnabledChanged`](https://learn.microsoft.com/en-us/uwp/api/windows.ui.viewmanagement.uisettings.animationsenabledchanged?view=winrt-26100) through a retained typed registration, not desktop observation or polling. The event requires Windows 10 version 2004; unavailable registrations leave per-presentation preference reads working. A weak-panel UI bridge ignores re-enabling (no replay), closes its delivery fence before revoking the native registration and suppresses queued work after teardown or registration failure. A real testing-backend event loop verifies worker delivery and both fences; unrelated desktop effects are forbidden by the host fixture. Windows event delivery/revocation still needs native runtime verification. Fade-out and the saved extreme-performance control remain incomplete, not substituted with delayed cleanup.

Dock start/application/window tiles and the genuine toolbar settings action now request this shared native surface from real pointer hover, forwarding full bounded labels and window-relative tile bounds. One retained weak-owner timer implements 100ms enter/leave delays; stale leaves cannot dismiss a newer tile or the other owner surface. Placement reads current owner origin/scale at presentation, flips near monitor edges and clamps to full physical monitor bounds, including negative origins. Click, disable, model refresh, fullscreen, geometry changes, interactive menus and teardown cancel pending/visible hints. Neither scheduling nor dismissal observes the desktop or requests focus.

Wheel input dismisses stale tooltip anchors while rejecting the tile's scroll event so the parent really scrolls. Overflowing desktop docks use wheel/scrollbars rather than mouse-pan interception, preserving immediate tile button-down callbacks. The real software renderer verifies this with a genuinely overflowing model at 2x, alongside click, disable and full-label/bounds forwarding.

The existing `TileButton` now explicitly acquires internal item focus on pointer-down: `TouchArea.forward-focus` alone did not focus its zero-sized sibling `FocusScope`, and a real dock renderer scenario reproduced the missed Space activation. It uses Slint's [documented focus reasons](https://docs.slint.dev/latest/docs/slint/reference/keyboard-input/focusscope/) rather than a global input hook: pointer focus suppresses the outline, keyboard/programmatic focus reveals it, and window/popup reactivation preserves the previous presentation. The keyboard scope follows the tile's enabled state so Tab skips busy/stale entries. The outline has the pinned shared stylesheet's 2px width and 2px gap, not an adjacent border. Light/dark 1x/2x real component tests cover pixels, pointer/Space activation, focus loss/restoration, Tab routing, disabled traversal and no idle repaint. This verifies item-tree behavior; native Windows foreground/accessibility and outlines at clipped scroll edges remain unverified.

Desktop backend creation uses [Slint's pre-creation Winit attributes hook](https://docs.rs/slint/1.18.1/slint/struct.BackendSelector.html#method.with_winit_window_attributes_hook) with inactive windows, avoiding activation by the first `show()` before role attachment. Explicit interactive foreground requests remain after validated attachment; utility mode keeps its normal creation behavior. The hover/delay conventions follow [the noninteractive tooltip pattern](https://ant.design/components/tooltip), not a claim that every reference override, arrow or animation is already reproduced. Real Windows GL/software composition, first-show foreground preservation and mouse pass-through still require native runtime/interactive verification. This development layer is not in the immutable alpha.10 package and does not complete appearance or full parity.


## Verification and limits

The official [preliminary headless testing backend](https://docs.slint.dev/latest/docs/rust/i_slint_backend_testing/) is a development-only dependency. Its version must exactly match Slint and the compiler, so all three are pinned to 1.18.1 and upgraded together. It tests callbacks and UI state without a display; it does not render pixels or validate Windows accessibility, focus, DPI, or antivirus behavior. The production binary must not include its testing or inspection facilities.

Development builds emit static widget metadata for headless element queries; release builds omit it. This is compiler metadata, not a running inspection server. Controller and text-safety tests do not need that metadata; the headless accessible-button assertion runs in debug builds. Real Windows accessibility remains an interactive release check.

The separate renderer tests instantiate the actual generated components on `MinimalSoftwareWindow`, dispatch pointer/keyboard/real 1x–2x scale-factor events, and render pixels. They check callback/accessibility metadata and that an unchanged surface requests no additional draw. `TESSERA_TEST_SCREENSHOTS` optionally exports PPM frames outside the repository. These tests are not screenshots of Windows' GL compositor and do not establish native screen-reader behavior or idle CPU/GPU measurements.

Shadow pixels require a different proof: the [pinned software renderer's `draw_box_shadow`](https://docs.rs/i-slint-renderer-software/1.18.1/x86_64-unknown-linux-gnu/src/i_slint_renderer_software/lib.rs.html#3059-3066) is unimplemented. Black RGB screenshots on a black backdrop also cannot certify shadow alpha. A separate opt-in Linux fixture uses the existing production FemtoVG renderer on an owned X11 display and Slint's supported window snapshot API. It requires a real `GraphicsAPI::NativeOpenGL` notification, failing on silent software fallback, and checks opaque bodies, transparent corners and black translucent shadows for the actual generated launcher, tooltip and context menu in both themes. The GL test is run in its own exact-test process at both `SLINT_SCALE_FACTOR=1` and `2`; no desktop host, shell attachment, taskbar/AppBar/session mutation or custom shadow implementation is involved. Optional exports composite the snapshot on synthetic neutral gray for review. These are genuine GL scene pixels on Mesa, not Windows driver/compositor, DPI/focus, pass-through or resource certification.

For an already-running **owned** X11 display with X11 keyboard and Mesa/OpenGL runtimes, run `DISPLAY=<display> LIBGL_ALWAYS_SOFTWARE=1 SLINT_SCALE_FACTOR=1 cargo +1.92.0 test -p tessera-ui --lib --locked --offline gl_render_tests::native_gl_frames_render_reference_shadow_alpha -- --exact --ignored`, then repeat with `SLINT_SCALE_FACTOR=2`. Only this one test runs in each process; do not mix its global backend with the default headless suite. The renderer feature is enabled in UI development dependencies; the Windows product already enables it independently.

The same guarded GL fixture also runs two bounded 200ms SDK one-shot stages on the genuine event loop before checking the launcher's three stock footer controls. Their Fluent color bindings animate for 150ms; immediate dark-theme snapshots previously retained light control pixels even though the final theme was correct. Settled light/dark snapshots at both scales verify opaque, appropriately light/dark idle control backgrounds and can be exported separately. This avoids a speculative Palette/style override. It is not proof that stock controls match the reference skins or that all stock animations honor reduced motion.

The taskbar lease protects against an owned GUI crash or heartbeat loss while its supervisor is alive. A hard termination of the supervisor cannot run Rust cleanup; the existing independent restore script recovers Winlogon, not an in-memory taskbar lease. Abrupt supervisor termination and independent taskbar recovery therefore remain explicit Windows release-gate scenarios, not a claimed crash-proof guarantee.

Current functional parity is incomplete: dock application grouping/instance counters, Seelen's default overlap-triggered auto-hide/pointer reveal, global Windows-key menu toggling, tray/media modules, folders, and plugins are not implemented. These remain required by the full acceptance contract above, not intentionally excluded features. Owned appbar position-change notifications are registered but are not yet consumed; competing appbars and dynamic DPI/display changes therefore need explicit Windows checks. Do not call this a complete or already pixel-certified 1:1 Seelen replacement.

Alpha.9 introduces this native visual/session redesign; the immutable alpha.8 remains the earlier alongside-Explorer dock. Optional experimental per-user shell activation and independent recovery remain specified in [the recovery decision](0006-per-user-shell-recovery.md). Neither version is a complete Seelen feature replacement: notification area, widgets, plugins, and automatic window layout remain absent. Hosted checks and software-renderer tests do not prove interactive Windows taskbar/appbar behavior, native backdrop appearance, accessibility, or idle resource use. The public unsigned test package is not evidence of Windows 11 or antivirus approval. Interactive testing and the [distribution trust gates](../distribution-and-trust.md) remain prerequisites for a consumer release.
